On October 5th, a script of mine stopped working. It counted how many times a day one of our services had been redeployed, and it did that with a simple command:

```bash
gcloud run revisions list --service ads-apiv2 --region us-central1
```

The answer was `HTTP 500: Internal error`. I tried the newer v2 API. Same error. Nothing had changed on our side, and Google's status page showed no incident. The service itself was up and answering requests normally.

The problem wasn't Google's. It was volume. And the volume was ours.

## What a revision is

In Cloud Run, a **service** is the thing with a name and a URL. A **revision** is an immutable snapshot of it: the container image plus the configuration at that moment, memory, CPU, environment variables, minimum instances. Every deploy creates a new revision, and traffic moves to it. The previous one stays there, idle.

An idle revision doesn't run, doesn't scale, isn't billed. The [documentation](https://docs.cloud.google.com/run/docs/managing/revisions) says so explicitly, and also says there is a maximum of 1,000 revisions per service, with older ones deleted automatically beyond that.

This creates an odd incentive. Since old revisions cost nothing, nobody has a reason to delete them. And since the ceiling is high, nobody reaches it early. When you do reach it, you find out the automatic garbage collection isn't as punctual as that sentence suggests. We found services with 1,100 listable revisions, and `ads-apiv2` went past a thousand without anything being removed.

## How we got to a thousand

`ads-apiv2` gets about fifteen deploys a day. Not because anyone touches it fifteen times a day. It lives in a Firebase Functions codebase alongside 78 other functions, and Firebase redeploys the whole codebase on every merge. Any change to any neighboring function creates a new revision of the API. On top of that, for a while, a scaling routine created three more revisions a day by adjusting the minimum instance count.

Fifteen a day, seventy days: a thousand revisions. The revision serving traffic that day was named `ads-apiv2-02142-ref`. The number in the middle is the service generation. It had been modified 2,142 times since it was created.

None of this showed up anywhere. There is no "accumulated revisions" chart in the console, no alert. The first symptom was a read API breaking.

## The first cleanup, by hand

With listing dead, the way out was to rebuild the list of revisions from Cloud Run's audit logs, which record every creation, and cross it with the date. That produced 728 revisions older than thirty days with no traffic. I deleted them in parallel, four at a time:

```bash
cat delete-plan.txt | xargs -P 4 -I{} gcloud run revisions delete {} --region us-central1 --quiet
```

Listing came back. 339 revisions were left. Problem solved for one service, for one month.

The obvious question came next: how many other services were on the same road?

## 373 services

The project has 373 Cloud Run services. A good share of them don't look like Cloud Run at first glance: every second-generation Cloud Function is a Cloud Run service underneath, with the same revisions and the same ceiling. The 79 functions in that codebase, for instance, are 79 services, and all of them receive the same fifteen deploys a day.

In a first read-only test on 14 of those services:

| | |
|---|---|
| Existing revisions | 10,854 |
| Deletion candidates (over 30 days, no traffic) | 7,183 |
| Services with more than a thousand revisions | 6 |

We could have repeated the manual cleanup, but the problem comes back every month. What was missing was a janitor.

## The janitor

It's a GitHub Actions workflow that runs every day at four in the morning, right after the nightly deploy window, so it never deletes anything underneath a deploy in progress. It walks every service in the project and deletes a revision only when **all** of these hold:

1. It was created more than 30 days ago.
2. It receives no traffic. That includes the serving revision, the latest ready one, the latest created one, and anything with a tag, even at 0%.
3. It's not among the 20 most recent revisions of the service.

The three rules are redundant on purpose. Any one of them alone would avoid deleting the wrong revision in most cases. Together, they avoid it in the cases we didn't think of.

There's a cap of 3,000 deletions per run, across the whole fleet, and the order is oldest first. The cap exists for two reasons. The Cloud Run admin API has a quota, and I don't want to find out what it is at four in the morning. And if there's a bug in the selection, it deletes at most 3,000 revisions before someone looks at the next day's table. With a fixed order, the cap always trims from the old side, which is the cheap side to be wrong on.

At the end, the job writes a table to the run summary: service, revisions, candidates, deleted, kept, errors. It's the only place that number exists.

## The surprise: the paginated API breaks too

The script doesn't use `gcloud run revisions list`, because that's precisely the command that dies above a thousand revisions. It uses the v1 API, in the Knative shape, asking for 200 revisions per page and following the continuation token. That had worked for rebuilding the `ads-apiv2` list.

In the first test against the real fleet, 14 of the first 43 services were skipped with `HTTP 500 listing revisions (page 1)`. Large services, all of them. I went to reproduce it by hand, varying the page size and repeating each call:

| Service | Page | 1st call | 2nd call |
|---|---|---|---|
| acquisitionmanagerdrawworker | 200 | 200 OK | 500 |
| acquisitionmanagerdrawworker | 50 | 500 | 200 OK |
| acquisitionmanagerdrawworker | 10 | 500 | 200 OK |
| adcreationjobworker | 200 | 200 OK | 500 |
| adcreationjobworker | 50 | 200 OK | 500 |
| adcreationjobworker | 10 | 500 | 200 OK |

Half the calls fail. Page size doesn't matter. Every call takes close to 5.5 seconds, success or failure, which suggests something on the other side scans the whole set before returning the page, and sometimes doesn't finish in time.

The fix is the most boring and the most effective one: try again. Up to five attempts per page, with growing waits, and only for network failures, 429 and 5xx. A real 404 or 403 still fails immediately, because repeating changes nothing. With that, the same 14 services listed without a single warning, with six pages retried in total.

The lesson here isn't about retries. It's about the test. The script had been exercised against fake `gcloud` and `curl`, in five scenarios, and passed all of them. The fakes never returned 500 half the time, because I didn't know the API did that. A dry run against the real system, one that only lists and never deletes, found in ten minutes what the mocks would never have found.

## Least privilege

The workflow runs as a service account that already existed for another CD task. Before granting anything new, I looked at what it had: a single role, read and write on objects in a deploy-state bucket. No Cloud Run permission at all, not even read.

The shortcut would be `roles/run.developer`, which covers everything. But `run.developer` also allows deploying, and this service account can be assumed by any workflow in the repository through Workload Identity Federation. Giving deploy rights to a revision janitor is giving deploy rights to the whole repository.

What it got was `roles/run.viewer`, to list and read, plus a custom role with exactly one permission:

```bash
gcloud iam roles create cloudRunRevisionJanitor \
  --project brendi-app \
  --permissions run.revisions.delete
```

One detail that cost an attempt: the project's IAM policy had conditional bindings, and in that case `gcloud` refuses to add a binding unless you explicitly say `--condition=None`. It's a good guard. It wants to be sure you didn't forget a condition.

## Fail loud

Automation that runs by itself at night has a specific failure mode: it runs, does nothing, and stays green. Missing permission? Green. API down? Green. Nobody looks, and six months later listing breaks again.

So the job only goes red in two situations: when it can't list the services, or when **every** attempted deletion fails. That second case is exactly the symptom of a missing permission, and it needs to hurt. A single service with an error, on the other hand, becomes a warning and a row in the table, and the rest of the fleet moves on. One flaky service can't block the other 372.

## What GitHub won't let you do

One last test was missing: run the workflow for real, as the service account, in read-only mode, before merging. You can't. `workflow_dispatch` only works if the workflow file already exists on the default branch. The [documentation](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_dispatch) is direct about it, and `gh workflow run` returns a polite 404.

So the sequence becomes: test locally in dry-run mode with my own account, merge, trigger the workflow manually in dry-run mode as soon as it exists on `main`, check the table, and only then let the four-in-the-morning schedule delete. If something is wrong in that window, `gh workflow disable` takes care of it.

## What stays

**Resources that cost nothing accumulate in silence.** Idle revisions, old snapshots, images in the registry, logs without retention. If there's no bill, there's no owner, and if there's no owner, only the provider's limit will warn you.

**Test against the real system before trusting the mocks.** Mocks reproduce what you already know. A dry run that only reads costs almost nothing and finds what you didn't know.

**Least privilege is cheap now and expensive later.** A custom role with one permission is one command. Removing `run.developer` from a service account ten workflows already use is a week.

**Automation that runs on its own needs to fail loud.** The worst outcome of a cleanup job isn't deleting too much. It's staying green while deleting nothing.
